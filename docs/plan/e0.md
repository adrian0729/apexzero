# E0: five seeds × 1B steps on `generator-v1` and `sim-v1` (run plan, DRAFT)

**Status.** DRAFT, 28 Oct 2026. Nothing here has run. E0's GPU budget is **not approved**: it goes to the user with Section 4's estimate. The recipe and the gate were fixed earlier (#10, #12, #13, GW-4; follow-through Sections 4 and 11), so this plan adds only the seeds, the checks and the box. E0 is the follow-through plan's Phase 4 training item, on the critical path to the lockbox.

## 1. The runs

- **5 runs**, seeds **50–54**, named `e0-s50` … `e0-s54`. No other study uses these seeds: the runs on disk use 0–4 and 10–14, VG-1's pilots 15–16, GW-3 20–29 and VG-1 30–49.
- **Each run:** `scripts/train_dr.py --steps 1e9 --seed <s> --name e0-s<s> --real-widths`, with every other argument `train_dr.py`'s default.
  - `--real-widths` with no `--real-widths-from` is `generator-v1`: copied R-dev width profiles, all 12 (GW-4, `docs/findings/gw4.md`).
  - No `--tilt-*` flag: v1, E0's curvature variant (decided 27 Oct 2026, before GW-3's tag).
  - `--vg-coef` stays 0: the value-gradient term is not in E0's recipe (VG-1 prereg Section 6, #5).
  - No training-only termination margin (`sim-v1`; GW-5 did not run).
- A 1B run anneals its learning rate and entropy over its own 1B steps, so it is not a continued 200M run (follow-through Section 7.4, GW-6).
- Each run keeps `train_dr.py`'s 16 log-spaced checkpoints and writes its end-of-run `eval_rdev.json` (10 laps per R-dev circuit, the default car, against the s-OCP lap). The evaluation reads R-dev only, and R_TEST is never touched.

## 2. The checks (before the launch, and in the manifest)

- **The tags.** E0's launch commit descends from `generator-v1` and `sim-v1` (both on `f7c9240`), and the code that defines them is byte-identical to the tag's.
  - That code is `scripts/train_dr.py` and its import closure, by directory: `src/apexzero/__init__.py`, `agents/`, `env/`, `eval/`, `oracle/`, `tracks/` and `vehicle/` (measured 28 Oct 2026 by loading `train_dr.py`; a test keeps the list complete). It also includes `src/apexzero/ocp/` (the end-of-run evaluation unpickles each R-dev circuit's OCP lap, which loads `apexzero.ocp`), `scripts/_bootstrap.py`, the queue (`scripts/gpu_round.sh`, `scripts/round_manifest.py`), E0's own scripts (`scripts/e0_runs.py`, `scripts/e0_gate.py`, checked against `e0-train-v1` only) and the environment's pins (`uv.lock`, `pyproject.toml`).
  - Other packages under `src/apexzero/` (the maze, costate and interpretability code) may change after the tags, because E0 never loads them.
  - The tags' commit is pinned as `f7c924002927374423ba44a476a23272a5ba2691`. Both tags must peel to it, locally and on origin.
- **The data.** On the box and on the Mac:
  - the 12 R-dev centreline files `data/tracks/tumftm/<circuit>.csv` must match the sha256 in `gw4.md` Section 3;
  - the 12 R-dev OCP reference files `outputs/ocp/<circuit>.pkl` must match the table below.
  
  Both sets go into the box's sha256 list, by explicit name, and the manifest checks them. They are measured on the Mac on 28 Oct 2026. The OCP files give only the descriptive lap-time gap, but a broken one would crash the end-of-run evaluation.

## 3. The gate (#10, fixed before any E0 run)

- **The gate passes** if the median seed completes at least 10 of the 12 R-dev circuits at its final checkpoint.
  - A circuit counts as completed when completion > 0.5 over 10 laps in the run's `eval_rdev.json`, as in GW-3 and VG-1.
  - No checkpoint is chosen on R-dev: the gate reads only the final checkpoint (GW-1 showed that R-dev completion peaks at slow early checkpoints).
- **A run that fails** is re-run once from scratch by the queue. A seed that fails twice is listed in `outputs/e0/failures.json` (status `failed`, with the reason from its logs, committed before the gate is read) and counts as 0 completed circuits, so a missing seed can only lower the median, and it is reported. A run that finishes with a non-finite parameter or metric is read as it is: its `eval_rdev.json` decides its count, and a run with no `eval_rdev.json` counts 0.
- **The label.** E0 trained on the R-dev circuits' own width profiles, so every R-dev number for E0, the gate's result and each seed's count among them, is labelled **"in-sample for widths"** wherever it is reported (`gw3.md` Section 1 lists what the label covers).
- **The reading** is computed once by `scripts/e0_gate.py gate`. It writes `outputs/e0/gate.json`, with a lock that is never removed, and the result is reported in `docs/findings/e0.md`.
  - The record holds each seed's count and its per-circuit completion, the median, and pass or fail.
  - As descriptive extras, it holds the lap-time gap on completed circuits (IN-4's form) and the count of seeds reaching 10.

## 4. The box and the budget (for the user's approval)

- **The layout.** One `massedcompute_A6000_plus` (1 × RTX A6000, $0.68/h on 27 Oct 2026; the lead checks the price before creating it), with all 5 runs at once at 5 lanes per GPU (XLA memory fraction 0.18, as VG-1's main run used).
- **The estimate,** from the runs on disk:
  - GW-3's v1 `base` runs trained 200M steps in about 1,388 s at 4 lanes per GPU, about 144k steps/s per run and 576k per GPU.
  - At 5 lanes the GPU's total is about the same, so each run trains at about 115k steps/s. VG-1's `base` runs at 5 lanes, sharing the GPU with heavier runs, did 114–115k.
  - 1B steps then take about 8,700 s, so the queue takes about 2.4–2.5 h with the end-of-run evaluation (about 4 min).
  - With setup and pull-back, the box time is **about 2.8–3.2 A6000 GPU-hours, about $2**. The follow-through plan's figure was 3.5–4.
- **Faster layouts at a similar cost.** A `massedcompute_A6000_plusx2` (3 + 2 lanes) would end in about 1.6 h for about 3.2–3.6 GPU-hours. An x4 box would end sooner but leave GPUs idle, for about 4.5 GPU-hours.
- **The stop rule:** if the projected box time exceeds the approved estimate by more than 20% (GPU-hours, idle GPUs included), the lead pauses E0 and asks the user.
